# Event Correlation and Final Test

## Final Test: End-to-End Verification

To confirm that everything worked in a real-world scenario:

1. I disconnected my test PC (Kali) from the home Wi-Fi
2. I connected it to my **phone's hotspot** (simulating an external network)
3. I launched the SSH connection towards the Ngrok address:

```bash
ssh root@<ngrok_address> -p <ngrok_port>
```

4. Access to the Honeypot was granted
5. **Immediately** on the Wazuh Dashboard, the "Intrusion Detected" alarm was triggered (rule 100012, level 10)

The system is online, monitored, and fully operational.

## Event Correlation: From Scan to Alert

In a real SOC, events are not analyzed in isolation. Correlation consists of linking apparently separate events to reconstruct the attacker's **kill chain**. Here is how the different lab components logged my simulation:

### Simulated Attack Timeline

```
T+0s    Nmap SYN scan from the Kali machine
        +-- UFW log: 65535 SYN packets from 192.168.0.YYY (Kali)
        +-- Wazuh rule 5710 (level 3): "Attempt to scan open ports"

T+30s   Hydra brute force on port 2222
        +-- Cowrie log: hundreds of cowrie.login.failed in rapid succession
        +-- Wazuh rule 100011 (level 5): "Cowrie: Multiple failed login attempts"

T+2m    Hydra finds a valid password (root/12345)
        +-- Cowrie log: cowrie.login.success
        +-- Wazuh rule 100012 (level 10): "Cowrie: Login success on honeypot"

T+2m30s Interactive session: the attacker executes commands
        +-- Cowrie log: cowrie.command.input (cat /etc/passwd, wget, uname -a)
        +-- Wazuh rule 100013 (level 8): "Cowrie: Command executed in honeypot"

T+3m    Malware download attempt (simulated)
        +-- Cowrie log: cowrie.session.file_download
        +-- Wazuh rule 100014 (level 12): "Cowrie: File download attempt"
```

### Correlation Query on the Dashboard

To reconstruct the entire sequence on Wazuh Dashboard (OpenSearch Dashboards), this query filters all events related to a single attacker session:

```
data.cowrie.session: "a1b2c3d4e5f6" OR data.srcip: "XX.XX.XX.XX"
```

By sorting by `timestamp` in ascending order, you get the complete timeline: from the first failed login attempt, to the successful login, to the commands executed in the honeypot session, through to any file downloads. This is exactly the workflow a SOC L1 analyst would follow during the triage of a real alert.

### Correlation with Network Logs (UFW)

UFW logs (`/var/log/ufw.log`) complete the picture at the network level:

```
[UFW BLOCK] IN=eth0 OUT= MAC=XX:XX:XX SRC=XX.XX.XX.XX DST=192.168.0.XXX LEN=44
            TOS=0x00 PREC=0x00 TTL=64 ID=54321 PROTO=TCP SPT=54321 DPT=9200
            WINDOW=1024 RES=0x00 SYN URGP=0
```

**Reading the UFW log:**

| Field | Meaning |
|---|---|
| `[UFW BLOCK]` | The packet was blocked (after remediation) |
| `SRC=XX.XX.XX.XX` | Attacker's source IP |
| `DPT=9200` | Destination port - the attacker attempted to reach OpenSearch |
| `SYN` | TCP flag - this is the first packet of a handshake (scan) |
| `WINDOW=1024` | Window size typical of Nmap SYN scan (tool fingerprint) |

The correlation between the `SRC` in the UFW log and the `data.cowrie.src_ip` in the Wazuh alert confirms that the same IP first scanned the ports (blocked by UFW on 9200) and then focused on port 2222 (Honeypot, intentionally open).

> **Analyst's lesson:** A single alert never tells the complete story. Real analysis begins when you correlate events from different sources (firewall, honeypot, SIEM) to reconstruct the entire attack chain. This is the value of having a centralized SIEM like Wazuh: all logs converge to a single point, making correlation possible.
