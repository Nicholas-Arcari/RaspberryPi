# TLS/PKI: Encryption and Certificates in Wazuh

Wazuh uses TLS/SSL communication between all components. In an All-in-One setup (everything on the same host), the certificates are self-signed, but still necessary for transport encryption.

---

## How TLS Works and Why Wazuh Needs It

**TLS (Transport Layer Security)** is the protocol that encrypts communication between two endpoints. When Filebeat sends alerts to the Indexer, the traffic goes over HTTPS (HTTP + TLS). Without TLS, the alerts (which contain IPs, usernames, honeypot passwords) would travel in cleartext over the network.

The TLS 1.2 handshake (used by Wazuh) proceeds as follows:

```
Filebeat (client)                                    Indexer (server)
       |                                                    |
       |-- ClientHello ---------------------------------->|
       |   (TLS version, supported cipher suites,           |
       |    random_client)                                  |
       |                                                    |
       |<-- ServerHello ----------------------------------|
       |   (chosen cipher suite, random_server)             |
       |                                                    |
       |<-- Certificate ----------------------------------|
       |   (server X.509 certificate: indexer.pem)          |
       |                                                    |
       |<-- CertificateRequest ----------------------------|
       |   (request for CLIENT certificate: mutual TLS)     |
       |                                                    |
       |   The client VERIFIES the server certificate:      |
       |   1. Is the signature valid? (verified with root-ca)|
       |   2. Does the CN/SAN match the hostname?           |
       |   3. Has the certificate expired?                  |
       |   4. Is it in the CRL (revocation list)?           |
       |                                                    |
       |-- Certificate (filebeat.pem) -------------------->|
       |-- ClientKeyExchange (pre-master secret encrypted  |
       |   with the server's public key) ----------------->|
       |-- CertificateVerify (client signature) ---------->|
       |                                                    |
       |   Both derive the master secret:                   |
       |   master = PRF(pre_master, random_c, random_s)     |
       |   -> 4 symmetric keys (encryption + MAC,           |
       |     one per direction)                             |
       |                                                    |
       |-- ChangeCipherSpec ------------------------------>|
       |<-- ChangeCipherSpec ------------------------------|
       |                                                    |
       |<=== Encrypted traffic (JSON alerts via HTTPS) ===>|
```

---

## Mutual TLS (mTLS): Bidirectional Authentication

In "normal" TLS (e.g., visiting https://google.com), only the **server** presents a certificate. The client verifies that the server is who it claims to be, but the server does not verify the client.

In Wazuh, **mutual TLS (mTLS)** is used: the **client** (Filebeat, Agent) must also present a certificate signed by the same CA. This ensures that:

- Only Filebeat with a valid certificate can send data to the Indexer
- Only agents with a valid certificate can communicate with the Manager
- An attacker who intercepts the traffic cannot inject fake alerts (they do not have the certificate)

## The X.509 Certificate: What It Contains

You can inspect a certificate generated by Wazuh:

```bash
openssl x509 -in /etc/wazuh-indexer/certs/indexer.pem -text -noout
```

Output (key fields):

```
Certificate:
    Data:
        Version: 3 (0x2)
        Serial Number: 1234567890abcdef
        Signature Algorithm: sha256WithRSAEncryption
        Issuer: CN = Wazuh Root CA            <-- Who signed it (our self-signed CA)
        Validity
            Not Before: Jan  1 00:00:00 2025 GMT
            Not After : Jan  1 00:00:00 2035 GMT  <-- Expiration (10 years default)
        Subject: CN = node-1                   <-- Certificate identity
        Subject Public Key Info:
            Public Key Algorithm: rsaEncryption
            RSA Public-Key: (2048 bit)
        X509v3 extensions:
            X509v3 Subject Alternative Name:   <-- SAN: valid IPs/hostnames
                IP Address:127.0.0.1
```

| Field | Meaning | Why It Matters |
|---|---|---|
| `Issuer` | The CA that signed the certificate | The client verifies that the Issuer is in its trust store (`root-ca.pem`) |
| `Subject (CN)` | Common Name - server identity | Must match the name the client uses to connect |
| `SAN` | Subject Alternative Name - alternative IPs/hostnames | Modern standard: TLS verifies the SAN, not the CN. If the IP `127.0.0.1` is missing, the connection fails with "certificate verify failed" |
| `Validity` | Validity period | An expired certificate is rejected. Common cause of "Wazuh won't start after a year" |
| `Serial Number` | Unique identifier | Used for revocation (CRL/OCSP) |

## Chain of Trust: How the Client "Trusts"

```
[Root CA] (root-ca.pem / root-ca-key.pem)
    |
    |  signs (with root-ca-key.pem)
    v
[Indexer Certificate] (indexer.pem)  <-- contains the Root CA signature
[Manager Certificate] (server.pem)  <-- contains the Root CA signature
[Dashboard Certificate] (dashboard.pem)
[Filebeat Certificate] (filebeat.pem)
```

When Filebeat connects to the Indexer:
1. The Indexer presents `indexer.pem`
2. Filebeat reads the `Issuer: CN = Wazuh Root CA` field
3. Filebeat looks up `Wazuh Root CA` in its trust store (`/etc/filebeat/certs/root-ca.pem`)
4. It verifies that the signature in the certificate was produced by the Root Càs private key
5. If verification passes -> connection accepted
6. If it fails -> "certificate verify failed" and connection refused

> **Why self-signed is fine in our case:** In a public environment (websites), certificates must be signed by a recognized CA (Let's Encrypt, DigiCert) because browsers have a pre-installed list of trusted CAs. In our lab, all components are on the same host and we control certificate distribution - a self-signed CA is sufficient and does not introduce additional risks.

**Common error:** If after regenerating certificates a component fails to start, verify that `root-ca.pem` has been copied to **all** directories (`/etc/wazuh-indexer/certs/`, `/etc/filebeat/certs/`, etc.). A single component with the old CA will cause TLS errors in the pipeline.
