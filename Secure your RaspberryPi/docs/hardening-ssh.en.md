# SSH Hardening: Configuration and Keys

SSH is the main entry point to the system. If an attacker compromises SSH, they have full access. Every directive in the configuration file has a direct impact on the attack surface.

For the deep dive on the SSH protocol (5 phases, KEX, fingerprint, known_hosts, challenge-response), see [protocollo-ssh.en.md](protocollo-ssh.en.md).

---

## sshd_config Configuration

```bash
sudo nano /etc/ssh/sshd_config
```

Here are the critical directives with an explanation of each:

```bash
# Force SSH protocol version 2
# SSH v1 has known vulnerabilities (CRC-32 compensation attack) and is deprecated
Protocol 2

# Disable direct root login
# An attacker must first guess a valid username, then perform privilege escalation
# Drastically reduces the effectiveness of bots that automatically try root/admin
PermitRootLogin no

# Disable password authentication
# Passwords are vulnerable to brute force. SSH keys use asymmetric cryptography
# (RSA 4096-bit or Ed25519) which makes brute force computationally infeasible
PasswordAuthentication no

# Enable public key authentication
# The client proves it possesses the private key corresponding to the public key
# registered on the server, without ever transmitting the private key over the network
PubkeyAuthentication yes

# Maximum time to complete login (in seconds)
# Prevents "hanging" SSH connections that consume resources
LoginGraceTime 120

# Verify that ~/.ssh permissions are correct
# If authorized_keys is readable by other users, SSH refuses to use it
StrictModes yes

# Disable host-based authentication (legacy, insecure)
HostbasedAuthentication no

# Reject empty passwords
PermitEmptyPasswords no

# Disable X11 forwarding if not needed
# Reduces the attack surface - X11 has a history of vulnerabilities
X11Forwarding no

# Disable TCP forwarding - prevents the Pi from being used as a proxy
AllowTcpForwarding no

# Disable compression - prevents CRIME/BREACH type attacks
Compression no

# Limit SSH access to users in specified groups only
AllowGroups root _ssh

# Paths to authorized_keys files (OMV adds its own)
AuthorizedKeysFile .ssh/authorized_keys .ssh/authorized_keys2 /var/lib/openmediavault/ssh/authorized_keys/
```

## Applying the Changes

```bash
sudo systemctl restart ssh
```

> **Before restarting SSH:** open a **second SSH session** and keep it open. If the new configuration has an error (e.g., `AuthorizedKeysFile` points to a wrong path), the current session would remain active and you could fix the error. Otherwise you risk locking yourself out of the system.

## Public Key Setup (if not already done)

On the **client** (your PC):

```bash
# Generate an Ed25519 key pair (more secure and faster than RSA)
ssh-keygen -t ed25519 -C "nick@homelab"

# Copy the public key to the Raspberry Pi
ssh-copy-id -i ~/.ssh/id_ed25519.pub pi@<RASPBERRY_IP>
```

**Why Ed25519 over RSA:**

| Algorithm | Key Size | Equivalent Security | Performance |
|---|---|---|---|
| RSA 2048 | 2048 bit | ~112 bit | Slow generation and verification |
| RSA 4096 | 4096 bit | ~140 bit | Very slow |
| Ed25519 | 256 bit | ~128 bit | Very fast, resistant to side-channel attacks |

Ed25519 uses the Curve25519 elliptic curve and provides security equivalent to RSA 3000+ bit with much shorter keys and faster cryptographic operations.
