# Firewall with UFW and Deep Dive into netfilter/iptables

**UFW (Uncomplicated Firewall)** is a frontend for `iptables` (or `nftables` on Debian 12+) that simplifies the management of network traffic filtering rules.

---

## How It Works at a Low Level: netfilter and iptables

UFW is a simplified interface for **iptables**, which in turn is the userspace frontend for **netfilter** - the packet filtering framework integrated into the Linux kernel. To understand why the order of UFW rules matters (and to debug when something isn't working), you need to understand the underlying architecture.

### The 5 netfilter Hook Points

Every network packet passing through the Linux kernel goes through a sequence of **hook points** where rules can intercept it:

```
                                    Local process
                                    (SSH, Wazuh, Pi-hole)
                                         ^    |
                                         |    |
                                      INPUT  OUTPUT
                                         |    |
Packet   --> PREROUTING --> Routing -->--+    +---> Routing --> POSTROUTING --> Network
incoming                    decision                decision                   out
                                |                        ^
                                |                        |
                                +------ FORWARD ---------+
                                   (packets in transit,
                                    not destined for this host)
```

| Hook | When It Triggers | Typical Use |
|---|---|---|
| `PREROUTING` | As soon as the packet arrives, before any routing decision | DNAT (port forwarding), destination IP modification |
| `INPUT` | After routing, if the packet is destined for a local process | **Inbound firewall** - where UFW primarily operates |
| `FORWARD` | If the packet must be forwarded to another interface (the host acts as a router) | Firewall for transit traffic (e.g., Docker containers) |
| `OUTPUT` | Generated by a local process, before outbound routing | Outbound firewall (rarely used) |
| `POSTROUTING` | After routing, just before leaving the interface | SNAT/MASQUERADE (used by WireGuard for VPN client NAT) |

### The 4 iptables Tables

Rules are not all in the same "container." iptables organizes them into **tables**, each with a specific purpose:

| Table | Purpose | Available Hooks | Used in Our Project |
|---|---|---|---|
| `filter` | Accept or drop packets (firewall) | INPUT, FORWARD, OUTPUT | **Yes** - UFW, Fail2ban |
| `nat` | Modify source or destination IP/port | PREROUTING, OUTPUT, POSTROUTING | **Yes** - Docker bridge (container NAT), WireGuard (MASQUERADE) |
| `mangle` | Modify packet headers (TTL, TOS, marking) | All 5 | No (advanced use, QoS) |
| `raw` | Mark packets to bypass connection tracking | PREROUTING, OUTPUT | No (advanced use) |

### Connection Tracking (conntrack): Stateful Firewall

iptables (and therefore UFW) is a **stateful firewall** - it does not evaluate each packet in isolation but keeps track of **connections**.

Practical verification - show connections tracked by the kernel:

```bash
sudo conntrack -L 2>/dev/null | head -5
# or
sudo cat /proc/net/nf_conntrack | head -5
```

Example output:

```
tcp  6 431999 ESTABLISHED src=192.168.0.50 dst=192.168.0.102 sport=54321 dport=22
     src=192.168.0.102 dst=192.168.0.50 sport=22 dport=54321 [ASSURED] use=1
```

The kernel tracks the **state** of every connection:

| State | Meaning | Example |
|---|---|---|
| `NEW` | First packet of a never-seen connection | TCP SYN, first UDP DNS query |
| `ESTABLISHED` | Packet part of an already-open connection | Packets after the SYN-ACK |
| `RELATED` | New connection related to an existing one | ICMP "port unreachable" message in response to a connection |
| `INVALID` | Packet that does not belong to any known connection | Malformed packets, anomalous TCP scans |

**Why it matters:** When UFW does `default deny incoming`, it actually only blocks `NEW` inbound packets (new connections from the outside). `ESTABLISHED` and `RELATED` packets pass through - otherwise you couldn't receive responses to your requests (e.g., browsing the web, running apt update). This is implemented by the automatic rule:

```
-A ufw-before-input -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
```

You can verify it:

```bash
sudo iptables -L ufw-before-input -n --line-numbers | head -10
```

### How UFW Maps to iptables: Practical Verification

When you write `sudo ufw allow ssh`, UFW generates:

```
-A ufw-user-input -p tcp --dport 22 -j ACCEPT
```

To see **all** iptables rules generated by UFW:

```bash
# Show the full INPUT chain (including UFW chains)
sudo iptables -L INPUT -n --line-numbers

# Show UFW user rules
sudo iptables -L ufw-user-input -n --line-numbers
```

The order of chains in the `filter` table:

```
Chain INPUT:
  1. ufw-before-logging-input   <-- Pre-rules logging
  2. ufw-before-input           <-- Automatic rules (conntrack ESTABLISHED, loopback)
  3. ufw-after-input             <-- Automatic post-user rules
  4. ufw-after-logging-input     <-- Post-rules logging
  5. ufw-reject-input            <-- Final reject
  6. ufw-track-input             <-- Tracking

Chain ufw-before-input (automatic rules, NOT modifiable by ufw):
  1. ACCEPT conntrack RELATED,ESTABLISHED  <-- Responses to already-open connections
  2. ACCEPT loopback (127.0.0.1)           <-- Local traffic
  3. DROP conntrack INVALID                <-- Malformed packets
  4. -> ufw-user-input                     <-- YOUR rules (ufw allow/deny)
```

This explains why the order of UFW rules is critical and why `ESTABLISHED` always passes: the conntrack rule is **before** the user rules in the chain.

## Basic Configuration

```bash
sudo apt install ufw -y

# Default policy: block all incoming, allow all outgoing
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow SSH (otherwise you lock yourself out!)
sudo ufw allow ssh

# Enable the firewall
sudo ufw enable
```

> **WARNING:** Run `sudo ufw allow ssh` BEFORE `sudo ufw enable`. If you enable the firewall without allowing SSH, you will lose access to the Pi. The only way to recover will be to connect a physical monitor and keyboard, or reflash the SD card.

## Verification

```bash
sudo ufw status verbose
```

Expected output:

```
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW IN    Anywhere
```

## Additional Rules for the Project

As you add services, you will need to open specific ports:

```bash
# Wazuh Dashboard (HTTPS)
sudo ufw allow from 192.168.0.0/24 to any port 443

# Portainer (HTTPS)
sudo ufw allow from 192.168.0.0/24 to any port 9443

# Wazuh Agent communication
sudo ufw allow from 192.168.0.0/24 to any port 1514 proto tcp
sudo ufw allow from 192.168.0.0/24 to any port 1515 proto tcp

# Honeypot (open to all - must be reachable by attackers)
sudo ufw allow 2222/tcp
```

> **Principle of least privilege:** Only open the ports that are needed, only from the IPs that need to access them. Management ports (SSH, Portainer, Wazuh Dashboard) should be limited to the local network (`192.168.0.0/24`). Only services that must be exposed to the Internet (Honeypot, VPN) should be open to all.
